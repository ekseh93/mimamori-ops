# 협업과 변경 관리

실제 여러 사람이 일한 것처럼 작성자나 리뷰 승인 기록을 만들지 않는다. 사용자=요구사항·학습·승인 담당, AI=구현·검증 보조이며 사용자 검토는 수행한 뒤 기록한다.

## 브랜치

- `main`: 초기 기획 기준선.
- `codex/mimamori-mvp`: 이번 구현과 테스트. 커밋은 검토 가능한 기능 단위로 남긴다.
- 이후 실제 작업 시 `codex/incident-drill`, `codex/aws-pilot` 같은 브랜치를 생성한다. 존재하지 않는 PR·리뷰·팀원을 완료로 적지 않는다.
- feature → PR → CI → 사용자 리뷰 → main → 승인된 배포. 현재 로컬 저장소이며 원격 PR·보호 규칙은 아직 없다.

## Definition of Done

- 인수 조건에 대응하는 테스트 통과, 실패 재현·수정 설명.
- 모의 데이터·로컬 실행·AWS 실행 근거 분리.
- 비용과 권한 범위 확인, 장애 대응·롤백 절차 존재.
- 사용자 본인이 DNS/TLS/HTTP/상태 저장/알림 흐름을 3분 이내 설명.
- AWS 관련 완료는 실제 배포·관측·알림·복구 증거를 확인한 뒤 표시.

## PR 리뷰 질문

1. 어떤 고객 문제나 실패 상황이 바뀌는가?
2. 실패가 재시도될 때 데이터와 알림은 어떻게 되는가?
3. IAM·네트워크·비용 범위가 넓어지는가?
4. 어떤 테스트가 이를 검증하며 AWS에서만 확인할 것은 무엇인가?
5. 이전 버전으로 되돌렸을 때 저장 데이터는 호환되는가?
